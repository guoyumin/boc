## 1. 背景与目标

苏黎世的《血染钟楼》玩家群每周组织一次线下活动。现状：

- 在微信群里用「接龙」报名，管理员根据人数决定当天的板子（剧本）。
- 剧本以 JSON 文件（avalon2.top / 官方 script 格式）和角色板图片（JPG）的形式在群里传播。
- 出席情况、谁鸽了、谁达成了什么"成就"，目前没有地方沉淀，全靠记忆和聊天记录。

本项目要做一个**轻量的群管理网站**，解决三件事：

1. **活动记录**：每周活动谁报名、谁实际来了（下午场 / 晚上场 / 全天）、谁报名了没来。
2. **资料存档**：每次活动用的板子图片和剧本 JSON 有地方保存和回看。
3. **成就墙**：管理员定义成就，玩家自己宣告达成，所有人能看到成就墙和个人成就。

**不是目标**：本项目不做线上游戏（魔典、说书人工具）、不做规则百科、不替代微信群聊。

### 1.1 规模假设

| 指标 | 估计值 |
|---|---|
| 活跃玩家 | 20–40 人 |
| 注册账号 | ≤ 60 |
| 活动频率 | 每周 1 次，每次 1–3 局 |
| 每次活动文件 | 1–3 张图片（≤ 10 MB/张）+ 1–3 个 JSON（≤ 1 MB） |
| 并发 | 极低，主要在活动前后集中访问 |

规模很小，架构以**简单、可备份、少运维**为第一原则（详见架构文档）。

### 1.2 使用场景

- 绝大多数访问来自**手机上的微信内置浏览器**（群里点链接打开）。界面必须移动端优先。
- 管理员在活动当天或次日用手机录入出席情况、上传图片和 JSON。
- 玩家偶尔打开看成就墙、看自己的出勤记录。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 活动 (Event) | 某一天的线下聚会，通常每周一次。一个活动可以有下午场、晚上场。 |
| 场次 (Session) | `afternoon` 下午场 / `evening` 晚上场 / `full` 全天。 |
| 剧本 / 板子 (Script) | 一套角色组合，如《随波逐流》《宏伟岩廊》。以 JSON 文件描述，配套一张角色板图片。 |
| 玩家 (Player) | 名册中的一个人，用群里的昵称标识。**不一定有账号**。 |
| 账号 (User) | 网站登录身份。一个账号最多绑定一个玩家。 |
| 管理员 (Admin) | 可以管理活动、名册、成就的账号。 |
| 初始管理员 (Owner) | 系统部署时创建的唯一最高权限账号，负责审批其他管理员。 |
| 成就 (Achievement) | 管理员预先定义的目标，例如"以小恶魔身份获胜""连续 10 周出席"。 |
| 成就解锁 (Unlock) | 某个玩家达成了某个成就的一条记录。 |

## 3. 用户与权限

| 角色 | 能做什么 |
|---|---|
| 访客（未登录） | 只能看到登录 / 注册页。（是否公开成就墙见 Q3） |
| 玩家（已登录，member） | 查看活动列表与详情、出席记录、文件；查看成就墙；宣告自己的成就；查看 / 编辑自己的资料。 |
| 管理员（admin） | 玩家的全部权限 + 创建 / 编辑活动、录入出席、上传 / 删除文件、维护名册、定义成就、确认 / 撤销成就解锁、重置用户密码、禁用账号。 |
| 初始管理员（owner） | 管理员的全部权限 + 审批管理员申请、直接授予 / 撤销管理员身份。owner 不可被降级或禁用。 |

权限规则：

- 权限是**账号级**的，与是否绑定玩家无关。
- 管理员操作在服务端校验，不依赖前端隐藏按钮。
- 关键管理操作（删除活动、撤销成就、修改他人权限）记录操作日志（谁、何时、做了什么）。

## 4. 范围划分

### MVP 第一阶段：账号 + 活动

- 注册 / 登录 / 登出、修改密码
- 管理员申请与审批
- 名册（玩家）管理，账号与玩家绑定
- 活动 CRUD、出席录入、报名未到统计
- 文件上传（板子 JPG / 剧本 JSON）、预览、下载

### MVP 第二阶段：成就

- 成就定义（管理员）
- 成就墙（所有人）
- 自己宣告成就、个人成就页
- 管理员确认 / 撤销 / 代为授予

### 第二期（MVP 之后）

- 游戏 log 上传（Markdown / 文本），与活动、场次关联
- 站内报名，替代或补充微信接龙
- 出勤统计（个人出勤率、连续出席、鸽子榜）
- 剧本 JSON 解析展示：角色列表、中文名、首夜 / 其他夜顺序
- 成就自动判定（依赖每局的结构化记录）
- 多语言（中 / 英）

### 明确不做

- 微信登录（需要企业认证的微信开放平台账号，不现实）
- 线上跑团 / 魔典功能
- 付费、AA 记账

## 5. 功能需求

编号规则：`AUTH-` 账号，`ROS-` 名册，`EVT-` 活动，`FILE-` 文件，`ACH-` 成就，`UI-` 界面。优先级 P0 = MVP 必须，P1 = MVP 尽量，P2 = 第二期。

### 5.1 账号与权限（AUTH）

| 编号 | 需求 | 优先级 |
|---|---|---|
| AUTH-01 | 用户可以用**用户名 + 密码**注册。用户名唯一，3–20 个字符；密码 ≥ 8 位。注册时填写显示昵称（默认等于用户名，建议填微信群昵称）。 | P0 |
| AUTH-02 | 注册需要**邀请码**（管理员在后台设置，可轮换），防止公网上随机注册。 | P0 |
| AUTH-03 | 登录后保持会话 30 天（HTTP-only cookie），支持登出。 | P0 |
| AUTH-04 | 用户可修改自己的密码（需输入旧密码）。 | P0 |
| AUTH-05 | 忘记密码：MVP 不做邮件找回，由管理员在后台**重置密码**（生成一次性临时密码，用户登录后强制修改）。 | P0 |
| AUTH-06 | 普通用户可以在个人页**申请成为管理员**，可填写申请理由。同一用户同时只能有一个待审申请。 | P0 |
| AUTH-07 | owner 在后台看到待审申请列表，可批准或拒绝。批准后该用户立即获得 admin 权限。owner 也可以直接在用户列表里授予 / 撤销 admin。 | P0 |
| AUTH-08 | owner 账号由部署时的环境变量创建（用户名 + 初始密码），首次登录强制改密。 | P0 |
| AUTH-09 | 管理员可以禁用 / 启用账号。被禁用的账号无法登录，但其绑定玩家的历史记录保留。 | P1 |
| AUTH-10 | 登录失败限流：同一用户名 10 分钟内失败 5 次后锁定 10 分钟。 | P1 |

### 5.2 名册 / 玩家（ROS）

设计要点：**玩家（Player）与账号（User）分离**。接龙里出现的人未必会注册；出席和成就都挂在玩家上，账号只是"认领"某个玩家的登录身份。

| 编号 | 需求 | 优先级 |
|---|---|---|
| ROS-01 | 管理员可以创建 / 编辑 / 归档玩家：昵称（唯一）、备注、可选头像 emoji。归档的玩家不再出现在录入下拉框，但历史数据保留。 | P0 |
| ROS-02 | 玩家可以有多个**别名**（接龙里名字不统一时用于匹配）。 | P1 |
| ROS-03 | 用户注册后，在个人页可以从名册里**认领**一个未被绑定的玩家；管理员也可以在后台绑定 / 解绑。一个玩家最多绑定一个账号。 | P0 |
| ROS-04 | 若用户未认领玩家，系统在注册时自动创建同名玩家并绑定（用户确认后）。 | P1 |
| ROS-05 | 玩家详情页：基本信息、出席记录（按活动倒序）、已解锁成就。 | P0 |

### 5.3 活动管理（EVT）

| 编号 | 需求 | 优先级 |
|---|---|---|
| EVT-01 | 管理员可以创建活动：日期（必填）、标题（默认"M月D日 血染"）、地点、备注、包含的场次（下午 / 晚上，默认都有）、状态（计划中 / 已结束 / 已取消）。 | P0 |
| EVT-02 | 活动列表页按日期倒序展示：日期、标题、剧本名（来自上传的 JSON）、出席人数、报名未到人数。 | P0 |
| EVT-03 | 活动详情页展示：基本信息、文件（图片预览、JSON 下载）、出席表。 | P0 |
| EVT-04 | **出席表**：每个玩家一行，两列状态：<br>· 报名：未报名 / 下午 / 晚上 / 全天<br>· 出席：未出席 / 下午 / 晚上 / 全天<br>管理员可以直接在表格里点选修改，即时保存。 | P0 |
| EVT-05 | 「报名未到」自动推导：报名 ≠ 未报名 且 出席 = 未出席。「部分未到」：报名全天但只出席一场，也要能看出来。 | P0 |
| EVT-06 | 管理员可以从名册里批量勾选玩家加入本次活动的出席表；也可以在表里直接新建玩家（应对临时来的新人）。 | P0 |
| EVT-07 | **接龙粘贴导入**：管理员把微信接龙文本粘贴进来，系统按行解析"序号. 昵称 [下午/晚上/全天]"，自动匹配名册（含别名），未匹配的列出来让管理员选择"新建玩家"或"对应到某玩家"，确认后批量写入报名状态。 | P1 |
| EVT-08 | 玩家可以查看所有活动的出席表（只读）。 | P0 |
| EVT-09 | 活动详情页显示"本次活动解锁的成就"（成就解锁记录可以关联活动）。 | P1 |
| EVT-10 | 删除活动需二次确认，并级联删除其文件与出席记录；操作写入日志。 | P0 |
| EVT-11 | 每场次可记录实际开的局数、每局剧本与说书人（结构化的"局"记录，为 log 和自动成就打基础）。 | P2 |

### 5.4 文件上传（FILE）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FILE-01 | 管理员可以给活动上传文件，类型：`board_image`（角色板图片，jpg/png/webp，≤ 10 MB）、`script_json`（剧本 JSON，≤ 1 MB）。每个文件可选标注所属场次（下午 / 晚上 / 不限）。 | P0 |
| FILE-02 | 上传的 JSON 做校验：必须是 JSON 数组，可含 `_meta` 对象（`name`、`author`）。解析出剧本名和作者用于列表展示；校验失败给出明确错误。 | P0 |
| FILE-03 | 图片在活动详情页内联预览（生成缩略图，点开看原图）；JSON 显示剧本名、作者、角色数量，并提供下载与"复制 JSON"按钮（方便导入 avalon2.top / 官方工具）。 | P0 |
| FILE-04 | 文件只对已登录用户可访问（不能通过猜 URL 匿名下载）。 | P0 |
| FILE-05 | 管理员可以删除文件；同一活动可以上传多个文件。 | P0 |
| FILE-06 | `game_log` 类型：Markdown / 文本文件（≤ 2 MB），页面内渲染 Markdown。 | P2 |
| FILE-07 | 剧本 JSON 解析展示角色列表（角色 ID → 中文名，需内置角色字典）。 | P2 |

### 5.5 成就（ACH）

| 编号 | 需求 | 优先级 |
|---|---|---|
| ACH-01 | 管理员可以创建 / 编辑 / 下架成就：名称、描述（达成条件）、图标（emoji 或上传小图）、分类（如 善良 / 邪恶 / 说书人 / 出勤 / 整活）、稀有度（普通 / 稀有 / 史诗 / 传说）、是否隐藏、排序权重。 | P0 |
| ACH-02 | **成就墙**：分类展示全部成就。每个成就显示：图标、名称、描述、稀有度、已解锁人数、解锁玩家头像 / 昵称列表（最多显示 N 个，点开看全部）。未有人解锁的成就以灰色显示。 | P0 |
| ACH-03 | 隐藏成就：在墙上只显示"???"，直到至少一人解锁后才公开名称与描述。 | P1 |
| ACH-04 | 已登录且绑定了玩家的用户，可以在成就详情里点击**「我达成了」**宣告解锁：可选关联活动、填写备注（例如"9/6 晚上场 以痢蛭获胜"）。同一玩家同一成就只能解锁一次。 | P0 |
| ACH-05 | 解锁记录有状态：`claimed`（自己宣告）/ `verified`（管理员确认）/ `revoked`（撤销）。宣告后立即出现在成就墙和个人页，标注"待确认"；管理员确认后去掉标注。撤销后不再显示但记录保留。 | P0 |
| ACH-06 | 管理员可以直接为任意玩家授予成就（状态直接为 verified），用于给没账号的玩家记成就。 | P0 |
| ACH-07 | 个人成就页：已解锁（按时间倒序）、未解锁、解锁进度（x / 总数，按稀有度加权的积分）。 | P0 |
| ACH-08 | 首页展示最近解锁动态："张三 于 9/6 解锁了〈史诗〉以痢蛭获胜"。 | P1 |
| ACH-09 | 成就可设置为"可重复"（如"担任说书人"），记录次数。 | P2 |
| ACH-10 | 基于活动 / 局记录自动判定成就（如连续出席 N 周）。 | P2 |

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| 部署 | 部署在用户自己的 VPS 上，域名 `boc.jiliguru.dev`，全站 HTTPS。 |
| 数据所有权 | 所有数据（数据库、上传文件）保存在 VPS 本地磁盘，不依赖第三方 SaaS。 |
| 备份 | 每日自动备份数据库与上传目录到 VPS 之外（对象存储或另一台机器），保留 30 天；有文档化的恢复步骤。 |
| 性能 | 页面首屏 < 2 s（欧洲网络、4G）；上传 10 MB 图片 < 30 s。 |
| 安全 | 密码用 bcrypt/argon2 哈希；所有写操作校验登录与权限；上传文件校验类型与大小，不执行；防 CSRF；依赖定期更新。 |
| 隐私 | 网站只对群内成员开放（邀请码注册）。不收集邮箱以外的个人信息（邮箱可选）。 |
| 可维护性 | 单人维护。一条命令部署 / 回滚；数据库迁移自动化；日志可查。 |
| 浏览器 | 微信内置浏览器（近两年版本）、Safari iOS 16+、Chrome / Edge 最新两个大版本。 |

## 7. 数据概念模型（摘要）

详细字段见架构文档 §4。核心实体与关系：

```
User 1 ──0..1 Player            账号可绑定一个玩家
Player 1 ──* EventAttendance    玩家在多个活动中的报名 / 出席
Event  1 ──* EventAttendance
Event  1 ──* EventFile          板子图片、剧本 JSON、（二期）log
Achievement 1 ──* AchievementUnlock ──* 1 Player
AchievementUnlock 0..1 ── Event 解锁可关联到某次活动
User 1 ──* AdminRequest         管理员申请
```

## 8. 待澄清问题

以下问题不影响开始搭骨架，但影响细节实现。每题都给出了**默认方案**，若不回复就按默认做。

| # | 问题 | 默认方案 |
|---|---|---|
| Q1 | 注册是否需要邀请码？（否则公网任何人都能注册进来看到大家的出勤） | **需要**，管理员后台可查看 / 更换邀请码。 |
| Q2 | 玩家与账号分离（名册模式）是否符合你的预期？替代方案是"只有注册了才能被记出席"，更简单但会漏掉不注册的人。 | **分离**。 |
| Q3 | 成就墙是否对未登录访客公开？ | **不公开**，全站需登录。 |
| Q4 | 成就宣告是否需要管理员确认才显示？ | **立即显示，标"待确认"**，管理员可确认 / 撤销。 |
| Q5 | 一个活动只上传一套板子，还是下午 / 晚上可能不同板？ | **允许多个文件，每个文件可标注场次**。 |
| Q6 | 是否需要记录每次活动的**说书人**是谁？（对"说书人"类成就有用） | MVP 在活动上加一个可选的"说书人"多选字段；结构化的每局记录留到二期。 |
| Q7 | 用户名 / 昵称是否直接用微信群昵称？ | 昵称建议填微信昵称，用户名自定。 |
| Q8 | 是否需要邮箱字段（未来找回密码用）？ | 可选填写，MVP 不发邮件。 |
| Q9 | 技术栈偏好：文档推荐 Next.js + SQLite（见架构文档）；若你更熟悉 Python，可改为 Django（自带后台）。 | **Next.js**。 |
| Q10 | 成就的初始清单由谁提供？需要先有一批种子成就。 | 你或管理群提供一份，我先放 10 个示例做演示。 |
| Q11 | 接龙的实际格式是什么？请贴一段真实接龙文本，用于实现 EVT-07 的解析。 | 按"序号. 昵称 时段"解析，时段关键词：下午 / 晚上 / 全天 / 晚。 |
