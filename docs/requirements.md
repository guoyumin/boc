## 1. 背景与目标

苏黎世的《血染钟楼》玩家群每周组织一次线下活动。现状：

- 先在微信群里问大家周六 / 周日哪个时段有空，管理员据此定日期。
- 定下来后在群里用「接龙」报名，管理员根据人数决定板子（剧本）。
- 剧本以 JSON 文件（avalon2.top / 官方 script 格式）和角色板图片（JPG）在群里传播。
- 每次活动会开好几局，说书人可能不止一人。出席、鸽子、谁拿了什么角色、谁达成了什么"成就"，目前没有地方沉淀。

本项目要做一个**轻量、无门槛的群管理网站**：

1. **时间投票**：每周发起一次"这周什么时候有空"的填写，管理员据此定周六还是周日。
2. **活动与报名**：定下来的活动进系统，玩家自己报名，或由管理员把微信接龙贴进来；活动后记录谁实际来了。
3. **游戏记录**：每次活动下记录每一局：剧本、说书人、玩家与角色；保存板子图片和剧本 JSON。
4. **成就墙**：管理员定义成就，玩家自己宣告，管理员确认后上墙。

**核心原则：参加活动不需要账号。** 打开网页填一个昵称就能投票、报名、记录对局。
注册是可选的，给常来的人用：绑定自己的昵称与别名，在一个地方看自己的报名、出勤和成就。管理权限要单独申请。

**不是目标**：线上游戏（魔典、说书人工具）、规则百科、替代微信群聊、微信登录。

### 1.1 规模假设

| 指标 | 估计值 |
|---|---|
| 活跃玩家 | 20–40 人 |
| 活动频率 | 每周 1 次，每次 2–4 局 |
| 每次活动文件 | 1–3 张图片（≤ 10 MB/张）+ 1–3 个 JSON（≤ 1 MB） |
| 并发 | 极低，活动前后集中访问 |

### 1.2 使用场景

- 绝大多数访问来自**手机上的微信内置浏览器**。界面必须移动端优先。
- 管理员在群里发链接，大家点开填时间 / 报名；管理员把结果文字复制回微信。
- 活动当天或次日，管理员录入出席；说书人自己录入自己那一局的剧本、玩家和角色。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 时间投票 (Poll) | 活动日期定下来之前的"哪个时段有空"调查，固定四个时段：周六下午、周六晚上、周日下午、周日晚上。勾选是多选，不是二选一。 |
| 活动 (Event) | 某一天的线下聚会。包含下午场和 / 或晚上场。 |
| 场次 (Session) | `afternoon` 下午场 / `evening` 晚上场 / `full` 全天。 |
| 游戏 / 局 (Game) | 活动中的一局。有剧本、说书人（可多人）、玩家及其角色。 |
| 剧本 / 板子 (Script) | 一套角色组合。以 JSON 文件描述，配套一张角色板图片。 |
| 玩家 (Player) | 名册里的一个人，用昵称标识。可以完全没有账号，昵称即身份。 |
| 账号 (User) | 可选的登录身份，绑定一个玩家档案。角色分 member / admin / owner。 |
| 管理员 (Admin) | 需登录。发起时间投票、定日期、贴接龙、录出席、确认成就。 |
| 初始管理员 (Owner) | 部署时创建的最高权限管理员，审批其他管理员。 |
| 成就 (Achievement) | 管理员预先定义的目标。按**角色**分组（通用 / 厨师 / 麻脸巫婆…），稀有度四档：普通 / 稀有 / 史诗 / 传说。数据源是 `docs/achievements.tsv`。 |
| 鸽 (No-show) | 报了名活动结束却没到场，包括本人事后取消。管理员 review 后可以「免鸽」。 |
| 成就宣告 (Claim) | 玩家声称达成某成就，需管理员确认后才显示在成就墙。 |

## 3. 用户与权限

| 角色 | 能做什么 |
|---|---|
| 游客（不登录） | 查看一切：时间投票结果、活动、出席表、游戏记录、文件、成就墙、玩家页。<br>填写：时间投票、活动报名与取消、录入游戏记录（剧本 / 说书人 / 玩家角色）、宣告成就。所有填写都以昵称署名。 |
| 注册玩家（member） | 游客的全部 + 在「我的」页里改自己的昵称和别名、看自己的报名 / 出勤 / 成就、改密码、申请当管理员。**没有任何管理权限。** |
| 管理员（admin） | 注册玩家的全部 + 发起 / 关闭 / 删除时间投票、决定活动日期并创建活动、编辑与删除活动、粘贴接龙导入报名、录入出席、免鸽、上传 / 删除文件、编辑或删除任何游戏记录、定义成就、确认 / 驳回成就宣告、维护名册。 |
| 初始管理员（owner） | 管理员的全部 + 审批管理员申请、改别人的角色、停用 / 删除账号、重置密码。owner 不可被降级或停用。 |

注册流程：`/register` 填昵称、用户名、密码，立即可用，不需要审批。填的昵称如果名册里已经有，就认领那条记录，以前的报名和成就都跟过来；已经被别的账号绑定的昵称不能重复认领。

管理员申请流程：先注册 → 登录 → 在「我的」页提交申请理由 → owner 在 `/admin/admins` 批准。

**关于"无登录"的风险**：任何人都能以任何昵称填写。这是有意的取舍，群是熟人圈，公开可见本身就是约束。补救手段：管理员可以改 / 删任何记录；成就上墙需确认；浏览器会记住昵称减少手滑。

## 4. 范围划分

### 原型（当前阶段）

界面全部页面可用，核心流程真实可操作（真实数据库），用于部署到 VPS 试用：时间投票、活动与报名、出席录入、接龙导入、游戏记录、成就墙与宣告、管理员登录。

### 已实现（原型之后补的）

文件上传（板子图片 / 剧本 JSON，含 magic bytes 校验、sharp 重编码与缩略图）、剧本 JSON 的 `_meta` 解析、成就真实清单。

### MVP 剩余

剧本 JSON 解析出角色列表供录入选择、管理员申请与审批、审计日志、备份脚本、名册合并。

### 第二期

游戏 log 上传、统计（出勤率、鸽子榜、角色胜率）、成就自动判定、多语言。

## 5. 功能需求

编号：`POLL-` 时间投票，`EVT-` 活动，`SIGN-` 报名与出席，`GAME-` 游戏记录，`FILE-` 文件，`ACH-` 成就，`ROS-` 名册，`ADM-` 管理员，`UI-` 界面。优先级 P0 = 原型必须，P1 = MVP，P2 = 二期。

### 5.1 昵称与身份（ROS）

| 编号 | 需求 | 优先级 |
|---|---|---|
| ROS-01 | 任何需要署名的操作都要填昵称。首次填写后浏览器记住（localStorage），之后自动带出，可随时改。 | P0 |
| ROS-02 | 昵称在提交时按名册匹配（去首尾空格、忽略大小写）；不存在则自动创建玩家。 | P0 |
| ROS-03 | 玩家页：出席记录、参与的局与角色、已确认成就。 | P0 |
| ROS-04 | 管理员可以给玩家添加别名（接龙里名字不统一）、重命名、归档。合并两个玩家还没做。 | P1 |
| ROS-05 | **注册玩家可以自己管理昵称和别名**（最多 5 个）：真名、英文名、群里的旧昵称都可以写进去。别名会显示在玩家主页上（"也可以叫：…"），这样想被人叫真名的人可以把真名写进来。接龙导入和昵称匹配都会认别名。 | P0 |
| ROS-06 | 昵称和别名在全名册里唯一：和别人的昵称或别名撞了会被拒绝并说清跟谁撞了。 | P0 |

### 5.2 时间投票（POLL）

参照 Xoyondo：一张表，列是时段，行是人，每人勾自己有空的格子。

| 编号 | 需求 | 优先级 |
|---|---|---|
| POLL-01 | 管理员发起一次时间投票：选择周末日期，标题按所选日期自动生成（可改），可选备注。**允许同时存在多个进行中的投票**，发起新的不会关掉旧的。 | P0 |
| POLL-02 | 四个固定时段：周六下午、周六晚上、周日下午、周日晚上。管理员可在发起时去掉某个时段（如周六有事）。 | P0 |
| POLL-03 | 玩家进入时间投票页：填昵称、勾选有空的时段、可选一句备注（"晚上只能到 9 点"），提交。同一昵称再次提交则覆盖。 | P0 |
| POLL-04 | 结果表：行 = 人，列 = 时段，勾 = 有空；每列底部合计人数，人数最多的列高亮。 | P0 |
| POLL-05 | 首页显示进行中的时间投票卡片，一键进入。 | P0 |
| POLL-06 | 管理员「定下来」：选择周六或周日（及包含的场次），系统创建对应活动，时间投票状态变为已决定并链接到活动。 | P0 |
| POLL-07 | 「复制到微信」：生成文本摘要，例如"本周活动定在 9月7日（周日）下午+晚上。有空的：张三、李四…"，一键复制。 | P0 |
| POLL-08 | 时间投票可以关闭、重新打开、删除（删除会连同填写记录，已定下的活动不受影响）。历史投票在 `/admin/polls` 里管理，公开页面不放入口。 | P0 |

### 5.3 活动（EVT）

| 编号 | 需求 | 优先级 |
|---|---|---|
| EVT-01 | 活动字段：日期、标题（默认"M月D日 血染"）、地点、开始时间（文本，如"下午一点半"）、包含场次（下午 / 晚上）、备注、状态（计划中 / 已结束 / 已取消）。可由时间投票创建，也可管理员直接创建。 | P0 |
| EVT-02 | 活动列表按日期倒序：日期、标题、剧本名（来自游戏记录）、报名数、出席数、报名未到数。 | P0 |
| EVT-03 | 活动详情页分区：基本信息 → 报名 / 出席表 → 游戏记录 → 文件 → 本次解锁的成就。 | P0 |
| EVT-04 | 删除活动需二次确认，级联删除报名、游戏、文件。 | P0 |
| EVT-05 | 「复制接龙」：由报名表生成微信接龙格式文本。 | P1 |

### 5.4 报名与出席（SIGN）

| 编号 | 需求 | 优先级 |
|---|---|---|
| SIGN-01 | **玩家自助报名**：在活动页填昵称、选时段（下午 / 晚上 / 全天）、可选备注（"晚上补位"），提交。再次提交覆盖；可取消报名。 | P0 |
| SIGN-02 | **管理员粘贴接龙**：把微信接龙文本贴进文本框，系统解析后展示预览（序号、昵称、识别到的时段、备注、匹配到的玩家 / 新建），管理员确认后批量写入。已有的报名按昵称覆盖。 | P0 |
| SIGN-03 | 接龙解析规则：<br>· 忽略 `#接龙` 行和标题行（第一个非序号行）。<br>· 每行 `序号[.、．]?\s*昵称\s*(备注)?`。<br>· 备注中含"下午"→ 下午；"晚上"→ 晚上；"全天"→ 全天；都没有 → 默认取活动标题里的场次（如标题含"下午"则默认下午），否则"全天"。<br>· 昵称为空或仅为标点（如"、"）的行视为占位，跳过并在预览中提示。<br>· 括号内文字（全角 / 半角）和昵称后的空格分隔文字作为备注保留。 | P0 |
| SIGN-04 | 出席表每人一行：报名时段、备注、**出席时段**（管理员点选：未到 / 下午 / 晚上 / 全天）。 | P0 |
| SIGN-05 | 自动标记：鸽（报了名、活动已结束、出席 = 未到）、部分未到（报全天只到一场）、未报名到场。 | P0 |
| SIGN-07 | 玩家可以自己取消报名。**取消不删记录**，标记为"已取消"并照样算一次鸽——报了又跑对组织者是有成本的。 | P0 |
| SIGN-08 | 管理员 review 之后可以「免鸽」：出席表里每行一个开关，免掉之后这次不再计入鸽子数，也可以撤销。真的临时有事就免掉，反复放鸽子就留着。 | P0 |
| SIGN-06 | 管理员可以在表里直接添加临时来的玩家。 | P0 |

### 5.5 游戏记录（GAME）

一次活动包含多局；说书人、玩家、角色、剧本都属于局。

| 编号 | 需求 | 优先级 |
|---|---|---|
| GAME-01 | 任何人（通常是说书人）可以在活动页「添加一局」：场次（下午 / 晚上）、剧本名、说书人（一个或多个昵称）、结果（善良胜 / 邪恶胜 / 未记录）、备注、记录者昵称。 | P0 |
| GAME-02 | 局内玩家列表：昵称 + 角色（文本）+ 可选座位号。逐行添加；昵称从本次活动出席 / 报名的人里快捷选择，也可手填。 | P0 |
| GAME-03 | 剧本名从最近用过的剧本里快捷选择，也可手填。 | P0 |
| GAME-04 | 若该局关联了剧本 JSON 文件，角色输入框提供该剧本的角色列表（角色 ID → 中文名）供选择。 | P1 |
| GAME-05 | 记录者本人（同昵称）和管理员可以编辑 / 删除该局。 | P0 |
| GAME-06 | 玩家页展示其参与的局：日期、剧本、角色、结果。 | P0 |
| GAME-07 | 角色阵营自动判断（善 / 恶），用于统计和成就。 | P2 |

### 5.6 文件（FILE）

| 编号 | 需求 | 状态 |
|---|---|---|
| FILE-01 | **只有管理员**能上传和删除文件（站点公开，不能开匿名上传端点）。上传时可一次选多个文件，可标注场次、可关联到本活动的某一局；类型按文件内容自动判断（图片 → `board_image`，JSON → `script_json`）。 | ✅ 已实现 |
| FILE-02 | 校验按 **magic bytes** 判断真实类型，不信任扩展名和浏览器给的 MIME：图片 jpg/png/webp ≤ 10 MB，JSON ≤ 1 MB，超限或类型不对给中文错误。JSON 还要求顶层是数组；首元素若是 `id === "_meta"` 的对象，取 `name` / `author` 存为剧本名与作者（`bootlegger` / `firstNight` 等多余字段一律容忍），其余元素（字符串或带 `id` 的对象）计为角色数。原文件原样保存不重写。 | ✅ 已实现 |
| FILE-03 | 图片用 sharp 重新编码（去掉 EXIF）、最长边限制 2500 px，另存一张最长边 400 px 的缩略图；活动页显示缩略图网格，点开看原图。JSON 显示剧本名、作者、角色数，提供「下载」与「复制 JSON」。 | ✅ 已实现 |
| FILE-04 | 文件公开可访问（与站点一致），但磁盘路径不可猜：`{活动 id}/{uuid}.{ext}`，绝不用用户传来的文件名做路径。取文件走 `GET /files/{id}`，`?thumb=1` 取缩略图；图片 `Content-Disposition: inline`，JSON 用 `attachment` 并带原始文件名；内容不可变，长缓存。 | ✅ 已实现 |
| FILE-05 | `game_log` 类型（Markdown ≤ 2 MB），页面内渲染。 | P2 |

> 上传走 Server Action，Next 默认 1 MB 的 body 限制装不下 10 MB 的图，
> 所以 `next.config.ts` 里把 `serverActions.bodySizeLimit` 调到 32 MB，
> nginx 的 `client_max_body_size` 也要跟着改（两处要一致）。

### 5.7 成就（ACH）

| 编号 | 需求 | 优先级 |
|---|---|---|
| ACH-01 | 成就的字段：名称、达成条件、**角色**（新建 / 编辑时从 177 个官方角色里下拉选，图标自动对应；非官方角色可手填）、**稀有度四档**（普通 / 稀有 / 史诗 / 传说）、**剧本专属**（`script_name`，空 = 全局成就）、是否隐藏、排序、是否下架。管理员在 `/admin/achievements` 里改。 | P0 |
| ACH-02 | 成就墙**按角色分组**：先「通用」，其余按清单里角色首次出现的顺序；每组标题是「角色图标 + 角色名 + 已解锁 x/y」，顶部有一条横向滚动的角色锚点条方便手机上跳转。剧本专属成就排在全局成就之后，按剧本名分块。每个成就显示图标、名称、稀有度、达成条件、已解锁者昵称；无人解锁灰显；隐藏成就未解锁前显示"???"。 | P0 |
| ACH-03 | 玩家在成就详情页「我达成了」：昵称、可选关联活动 / 局、备注。提交后状态 `pending`。 | P0 |
| ACH-04 | **待确认的宣告不出现在成就墙**。宣告者自己（同昵称）能在成就页看到"待确认"；管理员在后台看到待办列表，可确认或驳回（可填理由）。 | P0 |
| ACH-05 | 管理员可直接给某玩家授予成就（状态直接 `confirmed`）。 | P0 |
| ACH-06 | 同一玩家同一成就只能解锁一次。 | P0 |
| ACH-07 | 玩家页：已解锁成就、积分。**积分按稀有度**：普通 1 / 稀有 3 / 史诗 5 / 传说 10，玩家总分是已解锁成就的积分之和。 | P0 |
| ACH-08 | 首页显示最近确认的成就动态。 | P1 |
| ACH-09 | 基于游戏记录的自动判定（如"以 X 角色获胜"）。 | P2 |
| ACH-10 | 管理员可从表格（CSV / TSV，飞书或 Excel 直接复制也行）**批量新增**成就：先解析预览（新增几条、因重名跳过哪几条、哪几行读不出来），确认后一次性写库。**只新增**——重名跳过，不改已有成就，也不删。 | P1 |
| ACH-11 | 管理员可导出全量成就 CSV（带 id、解锁人数、首解者，UTF-8 BOM，Excel 直接打开），用来对账和备份。 | P1 |

**成就清单的数据源**：`docs/achievements.tsv`（制表符分隔，UTF-8）是**唯一数据源**，用户从飞书导出后覆盖它。
列为 `role` / `name` / `condition` / `stars` / `first_date` / `first_date_note` / `first_player`。
飞书里的稀有度是 1–5 星，脚本按 **1–2 星普通 / 3 星稀有 / 4 星史诗 / 5 星传说** 换算成站内四档
（当前清单：普通 10、稀有 22、史诗 15、传说 8）。
改完要跑 `npm run gen:achievements`，脚本会校验（空行、缺列、`stars` 越界、名称重复、日期格式）
并生成 `src/db/achievements-data.ts`；空库启动时 `seedAchievements()` 无条件把它写进 `achievements` 表，
`sort_order` 按表里的顺序递增。带 `first_player` 的行会同时写成 `confirmed` 的解锁记录，
日期不详的（`first_date_note`，如「已不可考」）存进 `achievement_claims.unlocked_at_text`，展示时优先于日期。

## 7. 数据概念模型

```
Poll 1 ──* PollResponse ──1 Player       每周时间投票与各人的可用时段
Poll 0..1 ── Event                         定下来后生成活动
Event 1 ──* EventSignup ──1 Player        报名 + 出席（每人一行）
Event 1 ──* Game                           一次活动多局
Game  1 ──* GameStoryteller ──1 Player    说书人可多人
Game  1 ──* GamePlayer ──1 Player         玩家与角色
Event 1 ──* EventFile                     板子图片、剧本 JSON；可关联到 Game
Achievement 1 ──* AchievementClaim ──1 Player   pending / confirmed / rejected
Admin（独立于 Player）                      仅管理员有账号
```

## 8. 已确认的决定

- 参加活动不需要账号，昵称即身份；全站公开可看。注册是可选的增值功能，不是门槛。
- 成就稀有度用四档（普通 / 稀有 / 史诗 / 传说），不用 1–5 星。
- 「预填」这个动词容易有歧义（"查看历史预填"读不通），统一叫「时间投票」；正式活动那一步仍叫「报名」，两者不混。
- 取消报名保留记录并算鸽，管理员 review 后可免。
- 技术栈 Next.js（见架构文档）。
- 成就宣告需管理员确认后才显示。
- 说书人、玩家、角色、剧本属于"局"，不属于"活动"。
- 正式域名 `play.zurich-boca.party`（2026-09-06 启用）。早期用过的临时域名保留为整站 301 跳转，群里散出去的旧链接还能用。
